# 전체 초기화·기본 시간표 적용일·공유 안내

> 이전 작업 기록입니다. 2026-11-12부터 자동 적용은 제거되었으며, 현재 동작은 [수동 시간표 불러오기](MANUAL_WEEK_IMPORT.md)를 따릅니다. 전체 초기화 기능은 유지합니다.

## 구현

설정 하단 ‘테스트’ 섹션에 빨간색 ‘테스트 데이터 초기화’를 추가했습니다. ‘테스트 데이터를 모두 삭제할까요?’와 되돌릴 수 없다는 설명을 표시하고, 취소 및 빨간색 ‘전체 초기화’를 제공합니다. 확인한 경우에만 저장소를 호출합니다.

`CalendarRepository.resetData()`는 기존 직렬 트랜잭션 경로로 `events`, `templates`, `timetable_presets`, `initialized_weeks`의 데이터를 지우고 내부 personal 캘린더만 남깁니다. 테이블·인덱스·스키마 버전·DB 파일은 유지하며 다른 테이블 및 다른 프로젝트 DB를 건드리지 않습니다. 중간 삭제나 결과 조회 실패도 모두 롤백합니다. 실제 사용자 DB에 초기화를 실행하며 개발하지 않았습니다. 테스트 DB만 사용했습니다.

성공한 스냅샷을 받은 Provider는 모든 소비자에 빈 데이터를 반영하고 클립보드·선택 날짜를 초기화합니다. 화면 하위 트리를 새로 마운트하여 이전 편집 초안·미리보기·내비게이션이 남지 않게 합니다. 초기화 진행 중 새 쓰기는 거절합니다. 실패하면 기존 스냅샷·클립보드·화면 상태를 유지하고 오류 안내와 재시도를 제공합니다. 재실행 시에도 빈 템플릿 상태를 유지하며 새 일정·시간표를 만들 수 있습니다.

세 번째 하단 탭은 ‘캘린더 공유’입니다. 기존 탭 스타일과 동일한 선택 색상·Safe Area를 사용하고 사람 두 명 모양을 코드로 그렸습니다. 공유 화면은 제목, ‘개발 중’, 요청한 설명 문구만 표시합니다. 공유 서비스나 계정 기능은 추가하지 않았습니다.

## 기본 자동 적용과 v3 이전

`timetable_presets.applyFromWeek`는 로컬 `YYYY-MM-DD` 형식의 월요일 또는 NULL입니다. 새 템플릿을 생성할 때는 기본 선택·적용일을 설정하지 않습니다. 기본으로 지정하는 트랜잭션에서 이전 선택 및 적용일을 비우고 새 선택에 다음 주 월요일을 기록합니다. 이미 기본인 항목을 다시 누르면 날짜를 미루지 않습니다. 목록에서 적용일 확인 및 기본 지정 해제가 가능합니다.

예를 들어 2026-11-10에 기본으로 지정하면 `applyFromWeek = 2026-11-16`입니다.

| 대상 주 | 결과 |
|---|---|
| 11/2–11/8 | 기존 데이터 보존, 자동 생성 없음 |
| 11/9–11/15 | 기존 데이터 보존, 자동 생성 없음 |
| 11/16 이후, 미초기화·수동 일정 없음 | 선택된 기본 일정 자동 복사 가능 |
| 11/16 이후, 빈 상태로 이미 열었거나 직접 작성·삭제한 주 | 기존 상태 유지 |

`ensureWeek()`는 미초기화, 수동 일정 없음, 활성 기본 선택 있음, `weekStart >= applyFromWeek`를 모두 확인합니다. 자동 생성 대상이 아니어도 열었던 주는 빈 주로 기록합니다. 기존 기록은 지우거나 재생성하지 않습니다. 기본 지정을 해제하면 이후 새 주는 빈 상태입니다. 날짜별 사본의 수정·삭제와 기본 시간표 변경은 서로 독립적입니다.

DB `user_version`을 3으로 올립니다. v2는 `ALTER TABLE ... ADD COLUMN applyFromWeek TEXT`와 기존 활성 기본값의 적용일 설정만 수행합니다. 과거 버전에는 정확한 기본 지정일이 없으므로 첫 업그레이드의 다음 주 월요일을 보수적인 기준으로 사용합니다. 기존 일정·템플릿·기본 선택·초기화 기록은 모두 보존합니다. v0/v1은 기존 다중 시간표 이전 후 같은 트랜잭션에서 v3까지 진행합니다. 이전 실패는 열 추가와 버전까지 롤백하며, 재시작 시 저장된 적용일을 다시 계산하지 않습니다.

## 변경 파일

- `src/app/settings.tsx`: 초기화 확인·진행·실패 및 하단 Safe Area.
- `src/app/(tabs)/_layout.tsx`, 새 `src/app/(tabs)/sharing.tsx`: 세 번째 탭 및 안내 화면.
- `src/hooks/use-calendar.tsx`: 초기화 성공·실패 상태, 클립보드 비우기, 화면 상태 초기화.
- `src/lib/repository.ts`: v3 이전·트랜잭션 초기화·적용일 저장·주별 생성 조건.
- `src/lib/presets.ts`, `src/types/calendar.ts`: 로컬 다음 월요일 계산 및 적용일 타입.
- `src/components/timetable/preset-list.tsx`: 적용 시작일 표시 및 기본 지정 해제.
- 새 `tests/fixtures/schema-v2.sql`, `tests/lifecycle.test.cjs`, `tests/lifecycle-ui.test.cjs`: 실제 v2 이전·자동 적용·초기화·화면 테스트.
- `tests/calendar.test.cjs`, `tests/presets.test.cjs`, `tests/timetable-ui.test.cjs`, `tests/ui-harness.cjs`: 기존 회귀 테스트의 날짜 고정 및 탭/안전 영역 테스트 지원.
- `README.md`, `docs/PRESETS_MIGRATION.md`, `docs/TOUCH_TESTS.md`, 이 문서: 현재 동작과 실기기 확인 절차.

`database.ts`는 같은 앱 DB만 계속 열며, `planning-screen.tsx`의 모든 주 진입은 강화된 `ensureWeek()`를 거칩니다. 두 파일을 추가 수정하거나 DB 경로를 바꿀 필요는 없습니다. 의존성 및 SDK 버전 변경은 없습니다.

## 검증

`npm run typecheck`, `npm run lint`, `npm test`, `npx expo install --check`를 모두 실행해 통과했습니다. 전체 자동 테스트는 86/86입니다.

추가로 `npx expo export --platform ios --platform android --platform web`도 통과했습니다. 새 공유 경로를 포함한 iOS·Android Hermes 및 웹 번들 생성이 성공했습니다.

추가 테스트는 초기화 취소·모든 삭제 단계/결과 조회 실패 롤백·다른 DB/스키마 보존·클립보드 및 화면 상태·초기화 후 재생성·파일 재시작, v1/v2 이전·다음 월요일 계산·과거/현재/기존 빈 미래/수동 미래 주 보존·기본 변경/해제·재시작 시 적용일 보존, 세 탭의 경로·선택 색상·Safe Area 설정과 공유 안내 문구를 확인합니다.

UI 테스트는 실제 React 컴포넌트/Provider와 실제 SQLite를 사용하며, 네이티브 뷰·제스처·Router 전달은 테스트 대역입니다. 아이폰에서 실제 탭 이동과 홈 표시기 주변 배치는 [실기기 체크리스트](TOUCH_TESTS.md)에 따라 확인해야 합니다.
