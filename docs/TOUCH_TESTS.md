# 터치 UI / 다중 시간표 / 공유 경계선 실기기 확인

이 문서는 아직 수행하지 않은 iPhone Expo Go 확인 절차입니다. 자동 테스트의 네이티브 뷰·제스처 대역으로는 실제 손가락의 인식, 스크롤과의 충돌, 햅틱 및 노치 주변 배치를 확정할 수 없습니다.

## 준비

```powershell
cd C:\Users\janghyunsung\Desktop\QuickTimeTable\mobile
npx.cmd expo start --clear --port 8082
```

PC와 iPhone을 같은 네트워크에 연결하고 QR 코드를 Expo Go로 엽니다. 주간 계획의 `확대 편집`에서 비어 있는 날짜에 테스트 일정을 만드세요. 아래 블록 조작 항목은 설정 → 기본 시간표 관리 → 원하는 시간표 편집에서도 반복합니다.

## 눌림 반응과 헤더

1. 블록 중앙에 손가락이 닿자마자 살짝 작아지는지 봅니다. 짧게 놓으면 원래 크기로 돌아가면서 편집이 열려야 합니다.
2. 350ms 정도 가만히 눌러 선택 테두리와 가벼운 햅틱을 확인합니다. 놓기 전에는 메뉴가 나타나지 않아야 합니다.
3. 누른 채 움직이면 블록이 조금 뜨고, 세부 움직임을 따라가며, 저장 시간은 30분 단위여야 합니다. 놓은 후 그림자·크기를 복원하고 메뉴는 나타나지 않아야 합니다.
4. 빠른 세로 스크롤, 확대 상태 가로 스크롤, 손가락 취소, 앱 전환, 화면 뒤로 이동 후 복귀를 시험합니다. 눌림·선택·떠 있는 모습이 남아 있으면 안 됩니다. 위·아래 손잡이 리사이징도 반복합니다.
5. 주간 화면과 템플릿 화면 모두 요일 행이 한 번만 나와야 합니다. 열 헤더의 요일을 누르면 그 요일을 선택하고 확대합니다. 가로 스크롤에서 헤더·열 및 시간 눈금 정렬, 오늘 강조를 확인합니다.

## 복사·붙여넣기

1. 블록을 짧게 탭하면 편집 창이 열리는지 확인합니다.
2. 중앙을 약 350ms 이상 누르고 가만히 놓습니다. 블록 위에 흰 글씨의 작은 `복사 | 삭제` 말풍선과 꼬리가 나타나는지 확인합니다. iOS 시스템 글꼴에서 두 글자 메뉴가 과하게 굵거나 크지 않은지, 구분선·38pt 기준 높이·짧은 등장 효과가 자연스러운지 봅니다. 접근성 글자 크기를 늘려 잘리지 않는지도 확인합니다. 커스텀 메뉴이므로 iOS 버전별 네이티브 텍스트 메뉴와 완전히 같지는 않습니다.
3. 메뉴 바깥을 탭하면 메뉴가 닫히고, 그 탭으로 새 일정이나 편집 창이 바로 열리지 않는지 확인합니다. 화면 상단·좌우 끝에 있는 블록에서도 메뉴가 Safe Area 밖으로 잘리지 않는지 확인합니다. 위쪽 공간이 부족하면 아래쪽으로 배치되어야 합니다.
4. 다시 길게 눌렀다 놓고 `복사`를 누릅니다. 빈 칸을 짧게 누르면 기존 새 일정 입력 창이 나타나야 합니다.
5. 빈 칸을 길게 눌렀다가 놓으면 `붙여넣기` 메뉴가 나타나는지 확인합니다. 앱을 새로 켜서 복사 전이라면 이 메뉴가 나타나면 안 됩니다.
6. 붙여넣은 블록의 제목·색상·길이는 원본과 같고 원본도 남아 있어야 합니다. 다른 빈 시간에도 반복해서 붙여넣습니다.
7. 다른 주·달력 탭·기본 시간표 화면을 다녀온 뒤 다시 붙여넣어 클립보드가 유지되는지 확인합니다.
8. 시작 칸은 비어 있지만 복사된 길이의 뒷부분이 다른 일정과 겹치는 위치에 붙여넣습니다. 충돌 안내가 나타나고 기존 일정과 원본은 바뀌지 않아야 합니다. 24:00을 넘기는 붙여넣기도 취소되어야 합니다.
9. 중앙을 길게 누른 뒤 다른 시간·요일로 이동하고 놓습니다. 이동만 저장되고 복사 메뉴는 나타나지 않아야 합니다. 같은 칸으로 돌아와 놓는 경우에도 메뉴가 나타나면 안 됩니다.
10. 350ms 전에 중앙이나 빈 공간을 빠르게 밀어 스크롤합니다. 복사·붙여넣기 메뉴나 편집 창이 뜨지 않아야 합니다. 확대 보기의 좌우 스크롤도 확인합니다.

## 삭제 확인

1. `삭제`를 누르면 ‘일정을 삭제할까요?’ 확인 카드가 열려야 합니다. 취소하면 블록과 저장 데이터가 그대로여야 합니다.
2. 다시 삭제하고 확인합니다. 선택한 블록만 사라지고 달력·일간 목록에도 반영되는지 확인합니다. 앱을 재시작한 뒤에도 삭제 상태를 유지해야 합니다.
3. 템플릿의 블록을 지우면 해당 템플릿에서만 없어져야 합니다. 다른 템플릿, 원본으로 이미 생성한 주간 일정은 남아 있어야 합니다.

## 다중 시간표와 불러오기

1. 기존 버전의 일정이 있는 상태에서 새 버전을 엽니다. 날짜별 일정·수정 내용·삭제한 주간 일정이 보존되고, 기존 기본 시간표가 ‘기본 시간표 1’로 목록에 나타나며 체크되어 있는지 확인합니다.
2. `+ 시간표 추가` → 빈 시간표를 선택합니다. 목록에 충돌 없는 번호 이름이 추가되고 개별 편집으로 이동해야 합니다. 이름을 ‘시험 기간’ 등으로 변경하고 블록을 만듭니다. 다른 시간표에는 블록이 나타나면 안 됩니다.
3. 목록의 체크를 다른 시간표로 옮깁니다. 체크가 한 개만 남아야 합니다. 이미 연 주와 수정한 주는 그대로이고, 아직 열지 않은 주에만 새 기본 시간표가 들어가야 합니다. 앱을 다시 열어 이름·기본 선택·모든 블록을 확인합니다.
4. 새 시간표 생성 시 ‘이전 시간표 불러오기’를 선택합니다. 주간 범위를 골라 미리보기를 봅니다. 스크롤·확대만 가능하고 새 블록 생성·이동·크기 조절·메뉴는 비활성 상태여야 합니다. 뒤로 가면 빈 템플릿이 추가되지 않아야 합니다.
5. 주간계획을 선택하고 불러오면 같은 요일·시간·제목·색상이 새 템플릿에 나타나야 합니다. 원본 주간계획은 그대로인지 확인합니다. ‘저장된 시간표’ 탭에서도 반복하여 복제본 수정이 원본에 영향을 주지 않는지 봅니다.
6. 블록이 이미 있는 템플릿에서 `시간표 불러오기`를 누릅니다. ‘현재 시간표를 불러온 시간표로 바꿀까요?’에서 취소하면 모두 유지되어야 합니다. 확인하면 해당 템플릿만 바뀌고 원본 및 다른 템플릿·실제 주간 일정은 유지되어야 합니다.
7. 일반 템플릿과 기본 템플릿을 각각 삭제합니다. 확인 전에 실제 데이터가 바뀌면 안 됩니다. 기본 템플릿 삭제 시 기본 지정 해제 안내가 나타나고, 이후 새 주는 빈 상태로 시작해야 합니다. 기존 주간 사본은 남아 있어야 합니다. 모든 템플릿을 삭제해도 실제 캘린더 일정은 유지되어야 합니다.

## 공유 경계선

같은 날짜에 A 09:00–10:00, B 10:00–11:00, C 11:00–12:00을 만듭니다.

| 동작 | A | B | C |
|---|---|---|---|
| A 아래쪽을 30분 아래로 | 09:00–10:30 | 10:30–11:00 | 11:00–12:00 |
| 원래 상태에서 A 아래쪽을 30분 위로 | 09:00–09:30 | 09:30–11:00 | 11:00–12:00 |
| 원래 상태에서 B 위쪽을 30분 아래로 | 09:00–10:30 | 10:30–11:00 | 11:00–12:00 |

- 드래그하는 동안 두 블록이 동시에 늘거나 줄고, 놓으면 저장되어야 합니다. 블록의 제목·색상과 다른 날짜의 일정은 바뀌지 않아야 합니다.
- B가 10:00–10:30인 경우 A 아래쪽을 더 내려도 B는 30분보다 짧아지지 않아야 합니다. C 등 다른 블록을 밀거나 삭제하면 안 됩니다.
- A 09:00–10:00, B 11:00–12:00으로 바꿉니다. A 아래쪽을 10:30으로 옮기면 B는 그대로여야 합니다. 같은 드래그에서 11:00에 닿은 후 11:30까지 내리면 B는 11:30–12:00이 되어야 합니다. 닿은 후 다시 위로 올릴 때도 두 블록이 경계선을 공유하는지 확인합니다.
- 단독 블록의 위쪽·아래쪽은 기존처럼 조절할 수 있어야 합니다. 00:00·24:00 바깥으로는 나가지 않아야 합니다.
- 이미 겹치는 블록을 만들고 모호한 경계선을 드래그합니다. 기존 겹친 일정을 삭제하거나 다른 블록을 임의로 바꾸면 안 됩니다.
- 경계선을 조절하다가 시스템 전환 등으로 제스처를 취소합니다. 손을 정상적으로 놓은 완료 동작과 구분되어 두 블록 모두 드래그 전 상태로 복원되는지 확인합니다.
- 변경 후 달력 탭과 일간 목록을 확인하고, 앱을 완전히 종료한 뒤 다시 열어 두 시간 변경이 함께 유지되는지 확인합니다.
- 기본 시간표에서 같은 테스트를 반복합니다. 이미 만들어진 주간 계획은 바뀌지 않아야 하며, 아직 열지 않은 주에는 변경한 원본이 적용되어야 합니다.

SQLite의 두 번째 쓰기 실패 시 전체 롤백과 Provider의 기존 스냅샷 보존은 자동 테스트에서 고의로 실패를 발생시켜 검증합니다. 실제 기기의 데이터를 손상시키거나 디스크를 채우는 방식으로 시험할 필요는 없습니다.
